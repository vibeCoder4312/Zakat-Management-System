# Architecture and Design Decisions (DECISIONS.md)

## 1. Schema & Database Decisions

- **PostgreSQL 16 & Naming Conventions**: Using PostgreSQL 16 with snake_case table and column identifiers. Primary keys are `bigint GENERATED BY DEFAULT AS IDENTITY` to enable preserving legacy IDs where applicable. Monetary columns use `numeric(18,2)`.
- **Flyway Database Management**: Schema and migrations are strictly managed through Flyway (`ddl-auto=validate` in Hibernate). Flyway migrations avoid hardcoded absolute host paths.
- **`zakat_year` Data Type**: Oracle stored `zakat_year` as `VARCHAR2(20)` in `zk_beneficiary` and `zk_allocation`. In PostgreSQL, `zakat_year` is typed as integer `int` across all tables (`zk_assessment`, `zk_beneficiary`, `zk_allocation`, `zk_planning`). Source string values were verified to be valid 4-digit years.
- **Denormalized Columns on `zk_allocation`**: The Oracle schema maintained denormalized text columns (`classification`, `beneficiary`, `school`, `paid_source_account`, `paid_via_agent`, `paid_via_employee`, `category`). These columns are retained in PostgreSQL on `zk_allocation` to guarantee 100% historical traceability back to the Excel and APEX source data, while establishing formal foreign key relationships (`classification_id`, `beneficiary_id`, etc.) with `ON DELETE RESTRICT`.
- **Beneficiary Code Generation**: Beneficiary code follows the format `BEN-` + 4-digit zero-padded number from sequence `zk_beneficiary_code_seq`. Since the CSV export did not include existing codes, codes will be sequentially assigned upon migration and the sequence will be reset to `MAX + 1`.
- **Assessment Recalculation Strategy**: No triggers (they would fire during bulk import). The service layer recalculates `zk_assessment` totals inside the allocation transaction using a JPQL aggregate with the same rule as the database function `fn_recalc_assessment(assessment_id)`. The function stays available for manual SQL use. (Calling it through a native `SELECT` from JPA failed and rolled back every allocation save.)

## 2. Reconstructed Database Views

> [!NOTE]
> Original Oracle DDL for database views (`zk_v_allocation`, `zk_v_year_summary`) was not supplied in the export files. These views have been reconstructed based on application behavior, trigger logic (`TRG_ZK_ALLOCATION_TOTALS`), and report requirements.

- **`zk_v_allocation`**: Reconstructed by joining `zk_allocation` with `zk_assessment`, `zk_classification`, `zk_beneficiary`, `zk_school`, `zk_source_account`, and `zk_agent`. Exposes `committed_amount = CASE WHEN status = 'PAID' THEN paid_amount WHEN status = 'PLANNED' THEN planned_amount ELSE 0 END`.
- **`zk_v_year_summary`**: Aggregates `zk_assessment` joined with allocations. Distinguishes Zakat-only paid totals from Sadaqah totals. Computes `unallocated = net_payable - total_paid - total_pending`, `pct_paid`, and `pct_pending` with zero-division safeguards.

## 3. Financial Measures & Scopes

To avoid mixing different financial scopes, the following definitions are strictly segregated:

| Measure | Scope / Formula |
|---|---|
| **Dashboard Hero Paid** | ZAKAT-only paid amounts (`fund_type = 'ZAKAT' AND status = 'PAID'`) |
| **Assessment Total Allocated** | ZAKAT committed amount (`status = 'PAID' ? paid : (status = 'PLANNED' ? planned : 0)`) |
| **Assessment Remaining Balance** | `net_payable - total_allocated_amount` (preserves historical negative values) |
| **Sadaqah Paid** | SADAQAH-only paid amounts (`fund_type = 'SADAQAH' AND status = 'PAID'`) |
| **Outstanding Amount** | `GREATEST(planned_amount - paid_amount, 0)` for non-cancelled allocations |
| **Classification × Year Pivot** | All-fund paid totals (`ZAKAT + SADAQAH`), expected total: ₹12,639,792.93 |
| **Category × Year Pivot** | All-fund paid totals (`ZAKAT + SADAQAH`), expected total: ₹12,639,792.93 |
| **Cash vs Online** | All-fund paid totals grouped by payment method (preserves null as "Not set") |
| **Zakat Assessment Total** | Grand total across 2020–2026: ₹12,205,127.32 (differs from all-fund ₹12,639,792.93) |

## 4. Source-to-Target Mapping & Reconciliation Decisions

- **Classification Mapping ("Medical" → "Medical Emergency")**: The allocation CSV uses `"Medical"` whereas the classification master contains `"Medical Emergency"`. During import, allocation rows with `"Medical"` are linked to the `"Medical Emergency"` master record ID while preserving the source string in staging.
- **Missing Category ("Donation")**: `Beneficiary Category.csv` lacked the `"Donation"` category, which is present on 9 beneficiary records and multiple allocations. `"Donation"` is seeded into `zk_beneficiary_category`.
- **11 Unregistered Institutes / Schools**: 11 school names appear in allocations that were not in `Institute.csv`. These are inserted into `zk_school` as master records to ensure strict foreign key integrity, flagged for administrative review.
- **Historical Payment Dates and Methods**: `paid_on` is NULL in 963 out of 965 allocation rows; `payment_method` is NULL in 684 rows. In accordance with data integrity principles, blank values remain strictly NULL.
- **Aurangabad Ration Kit Unknowns**: Beneficiaries `Unknown 1` through `Unknown 4` in 2026 are preserved verbatim.

## 5. Planning Storage & Reconciliation Rules

- **Planning Data Model**: `zk_planning` stores user-entered planning inputs (`zakat_year`, `plan_type`, `category`, `classification_id`, `planned_amount`, `remarks`). Derived aggregates (actual paid amount, remaining amount, allocation count, beneficiary count, source accounts, and prior years CY-1 to CY-5) are computed at query time.
- **No Destructive Rebuild**: Planning records are manually curated business records and will never be overwritten or recreated by automated background processes. Administrative reconciliation tools will operate in non-destructive preview mode only.

## 6. Security and Permission Matrix

- **Stateless JWT Authentication**: Passwords hashed with BCrypt.
- **Role Hierarchy**:
  - `ADMIN`: Full system administration, user management, assessment reopen/close, master management, planning management, and reconciliation.
  - `ACCOUNTANT`: Beneficiary management, allocation management, read access to planning, reporting, and exports.
  - `VIEWER`: Read-only access to dashboards, reports, and master lists.
- **Audit Columns**: `created_by`, `created_on`, `updated_by`, `updated_on` populated automatically via Spring Security context on mutation operations.

## 7. Frontend & UI Architecture Decisions

- **Color Palette & Theme**: Directly mirrors Oracle APEX Universal Theme styling with custom Islamic aesthetic accents:
  - Deep Green Primary: `#0B4A3F` (headers, primary buttons, hero section)
  - Secondary Teal: `#0F766E`
  - Gold Accent: `#C9A84C` / `#D4A017` / `#F5D77A` (lines, active borders, status badges, indicators)
  - Background Neutral: `#F2F6F4` / `#F7F5F0`
  - Text & Line: Dark ink `#10231F` with muted borders `#E1E8E5`
- **Indian Number Grouping**: Formatted using `Intl.NumberFormat('en-IN')` with ₹ symbol prefix (e.g., `₹41,05,212`). Negative balances are never clamped to zero and are explicitly styled in red bold text (`text-rose-600 font-extrabold`).
- **Year Filter Behavior**: Multi-select year filter component strictly serializes arrays of 4-digit numeric years (`[2020, 2021, ...]`). It persists selections in browser `localStorage` (`zakat_year_filter`) and never passes the literal string `"ALL"` to the backend.
- **Client-Side Auth State**: JWT stored in `localStorage` under `zakat_token`. The token payload is parsed on client load and expired tokens automatically trigger clean redirect to `/login`.
- **Foreign Currency Display**: Foreign currency (AED) amounts are formatted displaying both the foreign currency amount and the calculated INR equivalent using the recorded FX rate (e.g. `AED 1,000.00 (₹22,500)`).
- **Drilldown Planning Experience**: The Zakat Planning screen provides a multi-level experience with high-level variance summaries and interactive expandable drilldown rows revealing the individual constituent allocation payment lines.

## 8. Container Packaging & Deployment Decisions

- **Multi-Stage Dockerfiles**:
  - `backend/Dockerfile`: Multi-stage build with `maven:3.9.9-eclipse-temurin-17-alpine` compiling the application and packaging it into a hardened, non-root `eclipse-temurin:17-jre-alpine` runtime container.
  - `frontend/Dockerfile`: Multi-stage build with `node:22-alpine` using pnpm for fast production bundle generation, deployed to an `nginx:alpine` web server container with SPA fallback routing and `/api/` reverse proxy configuration.
- **Docker Compose Orchestration**:
  - `docker-compose.yml` orchestrates `db` (Postgres 16), `backend` (Spring Boot 3.3), and `frontend` (Nginx + React 18) with health checks (`pg_isready`), dependency order management (`service_healthy`), persistent named volumes, and bridge network isolation.


## 9. API Contract and Proxying (Session 2)

- The frontend calls the relative base path `/api/v1`. Vite (dev) and Nginx (Docker) proxy it to Spring Boot and forward the
  browser's `Host` header, so requests are same-origin and CORS never blocks them. `CORS_ALLOWED_ORIGINS` (origin patterns)
  only matters when the API is called directly from another host.
- Frontend types in `src/types/index.ts` mirror the backend DTOs field-for-field. When a DTO changes, update the type and let
  `tsc` point to every affected screen.
- 401 = not signed in / token expired (the UI returns to login); 403 = signed in but the role is not allowed (the UI shows a message).
